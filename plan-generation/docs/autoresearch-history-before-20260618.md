## 一、两个阶段

预案的 autoresearch 实际经历了**两个性质不同**的阶段：

### 阶段 A：设计层评估（analysis.md，2026-06-08，v1.0）

- **方法**：autoresearch 的"设计层面评估 + 执行风险分析"——**不实际跑 LLM**，而是人工/静态审视 SKILL.md 框架，识别 LLM 执行时可能偏离的风险点
- **结论**：设计框架 100% 完整（6 维 × 5 题），但列出 **5 个执行风险**（见下）
- **产出**：5 条 SKILL.md 改进建议（数据缺失降级/强化知识检索/模型合理性检查/多方案强制/HITL 强制）

### 阶段 B：执行层实验（changelog.md，v2.1 基线，3 轮）

- **方法**：真实跑 Hermes Agent，5 题 × 6 维，240s 超时
- **基线**：v2.1 = 24/30 (80.0%)，Q4 超时
- **3 轮实验**：

| 实验 | 改动 | 分数 | 状态 | 结果 |
|------|------|------|------|------|
| #0 基线 | 无（v2.1）| 24/30 (80%) | baseline | Q1-Q3,Q5 通过，Q4 超时 |
| #1 | 增加"预案解读高效查询"SQL 指导 | 23/30 (76.7%) | **discard** | Q4 通过，但 Q5 超时，总分下降 |
| #2 | 移除直接SQL示例，精简 SKILL.md | 23/30 (76.7%) | **discard** | Q5 仍超时，精简对超时无帮助 |

**最终**：回退到基线 80%，0 个实验保留。

## 二、阶段 A 识别的 5 个执行风险（设计层洞察）

这些是**不跑 LLM 就预见到**的偏离点，事后看多数命中：

| 风险 | 内容 | 后续是否验证 |
|------|------|-------------|
| 1 | LLM 忽略知识库检索，凭记忆回答 | 命中（v3.2 输出蓝图正是治这个）|
| 2 | DB 返回 NULL/空数据的边界处理 | 命中（v3.2 有"数据缺失处理"章节）|
| 3 | 模型计算失败/参数未率定 | 部分（仍依赖后端模型）|
| 4 | 安全约束被绕过 | 命中（v3.2 结尾段【安全校验】强制）|
| 5 | 多方案对比不充分（只生成1个）| 命中（v3.2 强制3方案）|

**得失点**：设计层评估（不烧 token）**前瞻性很强**，5 个风险里 4 个被后续验证并最终在 v3.2 落地。这是阶段 A 的最大价值——**低成本识别出真问题**。

## 三、阶段 B 的得与失（执行层实验）

### 得（正面）

1. **建立了真实基线 80%**——有了可对比的锚点
2. **识别出真正的瓶颈是"超时"而非"内容"**：3 轮实验反复证明，Q4/Q5 失败全是执行超时（20-240s 不稳定），不是 SKILL.md 写得不对
3. **否定错误优化方向**：实验 #1（加 SQL 指导）和 #2（精简内容）都没解决超时，证明"改 prompt 治不了执行超时"——这避免了后续在 prompt 上空转
4. **给出正确的根因归因**：超时是 Agent 查询策略问题（多次 SQL + DESCRIBE），解法应是 full_context 预取 + 加超时

### 失（教训）

1. **3 轮实验全 discard，0 保留**——优化没产生正向收益，效率低
2. **被"超时"这个**外部噪声**带偏**：实验本想优化引用/安全，但分数波动全由超时决定（Q4/Q5 随机超时），导致**信号被噪声淹没**，无法干净归因 prompt 改动的效果。这和本 session 发现的"Engine Busy 噪声"是同一类问题
3. **超时阈值（240s）设太短**：复杂题需要多次查询，240s 不稳定；事后建议加到 360-480s，但当时没做就回退了
4. **样本太小（5题）**：单题超时就能让分数掉 6.7%，噪声放大

## 四、阶段 B 给后续的关键启示（被本 session 验证）

阶段 B 的核心教训——**"prompt 优化治不了执行层的不稳定"**——在本 session 得到完整印证和深化：

| 阶段 B 的发现 | 本 session 的深化 |
|--------------|------------------|
| 失败是超时（执行不稳定），非 prompt | 失败真因是 Engine Busy（讯飞 endpoint），更精确 |
| 改 prompt 对超时无效 | 改 prompt 对 endpoint 无效，需 wrapper 退避重试（hermes-safe.sh）|
| 信号被噪声淹没，难归因 | 改用"分层看"（干净题 vs 污染题）+ 多次 run 取均值 |
| 超时阈值太短 | 加长到 600s + wrapper 内部退避 |

**可以说，本 session 的 v3.2 工作是把阶段 B 的"待办"全部兑现了**：full_context 预取（已在 SKILL.md）、加长超时（run_tests 600s）、治执行不稳定（hermes-safe wrapper）、输出蓝图治引用/安全（阶段 A 的风险1/4/5）。

## 六、总得失（两阶段合计）

### 得
- **设计层评估（阶段A）前瞻准确**：5 风险中 4 个命中并在 v3.2 落地
- **执行层实验（阶段B）排除了错误方向**：证明 prompt 改动治不了执行不稳定，避免空转
- **根因归因正确**：瓶颈在执行层（超时/endpoint），不在 skill 设计
- **沉淀了 v3.0 决策路由 + 查询策略**：直接呼应阶段B的优化建议

### 失
- **执行层 3 轮全 discard，0 正向收益**——autoresearch 循环被噪声（超时）击穿，没能产出 keep 的改动
- **样本小（5题）+ 噪声大（超时）= 不可归因**——这是阶段B效率低的结构性原因
- **memory 记录失真**（92.6% 无据）——提醒：autoresearch 结果要及时、准确沉淀，否则误导后续判断
- **当时没治超时就回退**——本 session 才补上（wrapper + 加超时）

## 七、一句话总结

本 session 之前的预案 autoresearch 分两阶段：**阶段A（设计评估）前瞻性强但纯静态**，**阶段B（执行实验）3轮全discard——不是优化失败，而是被"执行超时"噪声击穿、正确归因为"瓶颈在执行层不在prompt"**。这个归因本身是最大收获，它直接导向了 v3.0 的决策路由+查询策略，以及本 session v3.2 的 wrapper 防御+输出蓝图。**预案的优化史本质是：从"改 prompt"转向"治执行层不稳定"。**
