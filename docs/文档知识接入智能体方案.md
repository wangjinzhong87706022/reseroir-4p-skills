# 文档知识如何接入智能体 —— 落地方案

> 本文档回答核心问题：**已经提取的23万字文档知识，怎样真正让智能体"用起来"？**
>
> 关键原则：**不同类型的内容，用不同的方式喂给智能体**。不存在一种万能方法。

---

## 一、核心认知：内容分四类，各用各的喂法

把所有文档内容塞进一个"大文件"让智能体读，是最常见也最错误的做法。智能体的上下文窗口有限（几万到几十万token），且"大海捞针"会降低准确率。

正确做法是 **按内容形态分流**：

| 内容形态 | 桃曲坡文档中的例子 | 正确的喂法 |
|---------|------------------|-----------|
| **① 非结构化文本**（预案、规程、处置步骤描述） | 防洪抢险应急预案、调度规程、安全鉴定分析 | **RAG 检索增强** |
| **② 结构化数值**（曲线、阈值表、参数表） | 水位-库容-泄流曲线、预警阈值表、工程参数 | **数据库表 + 工具函数** |
| **③ 实体关系**（主数据、组织架构、人员） | 联防指挥部、抢险队伍、物资清单、监测站点 | **数据库 + 知识图谱** |
| **④ 规则流程**（四级响应、巡查频次、判断逻辑） | Ⅳ/Ⅲ/Ⅱ/Ⅰ级响应条件、巡查频次表 | **规则引擎 / 系统提示词** |

> 一个智能体通常 **组合使用** 这4种方式。例如四预智能体 = RAG（查预案）+ 工具函数（查曲线/算调洪）+ 规则（判预警级别）。

## 二、四种喂法详解（配桃曲坡真实数据）

### 喂法①：RAG 检索增强 —— 用于"查文档问答"

**适用场景**：用户或系统提问，智能体需要从几十万字文档里找到相关段落来回答。

**典型问题**：
- "大坝出现管涌，按预案怎么处置？"
- "溢洪道右岸高边坡的历史滑坡情况？"
- "Ⅰ级响应的启动条件和响应措施是什么？"

**实现流程**（5步）：

```
原始文档（PDF/MD）
    ↓ ① 切块(chunking)
文本块(每块300-500字，带重叠)
    ↓ ② 向量化(embedding)
向量(768维或1536维)
    ↓ ③ 存入向量库
向量数据库(Milvus/Chroma/PGVector)
    ↓ ④ 提问时检索Top-K相关块
召回的5-10个文本块
    ↓ ⑤ 拼进提示词送给大模型
最终答案
```

**桃曲坡具体示例 —— 切块**：

```
原文（《防洪抢险应急预案》第5.2.1节）：
"（7）管涌、流土抢护的措施
①反滤压盖：在背水坝脚附近险情处，抢筑反滤压盖，制止
地基土沙流失。一般适用于管涌或流土处数较多、面积较大..."

切成一个chunk（保留章节标题作为元数据）：
{
  "text": "（7）管涌、流土抢护的措施：①反滤压盖，在背水坝脚...",
  "source": "防洪抢险应急预案",
  "section": "5.2.1 各种险情及抢险调度方案",
  "topic": "管涌处置",
  "agent": ["应急响应", "智能巡检"]
}
```

**关键技巧**：
- **切块要按语义边界**（章节、段落、条款），不要机械按字数切，否则会把一个处置方案切成两半
- **保留元数据**（来源文档、章节、主题标签），检索时可过滤，回答时可溯源
- **表格单独处理**：水位-库容表这类别切碎，整表或按行存
- **混合检索**：向量检索（语义相似）+ 关键词检索（精确匹配"Ⅰ级响应"）结合，准确率最高

**向量库选型建议**：
- 原型/小规模（<10万块）：Chroma、FAISS（轻量本地）
- 生产/中规模：Milvus、Qdrant、PGVector（PostgreSQL扩展）
- 云服务：阿里云DashVector、腾讯云VectorDB（若用国内云）

**Embedding模型选型**：
- 中文优先：`bge-large-zh`（开源，效果好）、`m3e-base`
- 闭源API：通义千问text-embedding、智谱embedding
- ⚠️ 注意：水利专业术语多，通用embedding可能检索不准，必要时用领域数据微调

### 喂法②：数据库 + 工具函数 —— 用于"查数值、做计算"

**适用场景**：智能体需要精确的数值查询或数学计算。这类内容**绝对不能用RAG**（大模型查曲线会算错）。

**典型问题**：
- "当前水位787.2m，库容多少？能泄多少？"
- "预报来水200万m³，水位会涨到多少？"
- "要控制下泄500m³/s，闸门怎么开？"

**实现方式：把数据存成表/函数，让智能体"调用"它们**

**桃曲坡具体示例 —— 水位-库容-泄流工具函数**：

```python
# 把OCR/提取的曲线表存成结构化数据
CAPACITY_CURVE = {
    783.5: 2820, 784.5: 3020, 785.5: 3250, 786.5: 3485,
    787.5: 3719, 788.5: 3949, 789.5: 4175, 790.5: 4420,
}
DISCHARGE_CURVE = {
    783.5: 97, 784.5: 241, 785.5: 447, 786.5: 747,
    787.5: 1087, 788.5: 1507, 789.5: 1947, 790.5: 2331,
}

def get_capacity(water_level: float) -> float:
    """水位→库容（万m³），线性插值"""
    # ...插值逻辑...

def get_discharge(water_level: float) -> float:
    """水位→总泄量（m³/s）"""

def predict_water_level(current_capacity, inflow_volume):
    """根据来水量预测水位"""
```

**然后把这个函数注册为智能体的"工具"(Tool)**：

```python
# 智能体（以OpenAI/Claude function calling为例）
tools = [
    {
        "name": "get_capacity",
        "description": "根据水库水位查询库容(万m³)",
        "parameters": {"water_level": "水位高程(m)"}
    },
    {
        "name": "get_discharge",
        "description": "根据水位查询泄流能力(m³/s)",
        "parameters": {"water_level": "水位高程(m)"}
    },
]
```

智能体对话时**自动决定调用哪个工具**：
```
用户：现在水位787.2m，库容多少？
智能体（内部调用 get_capacity(787.2)）→ 返回约3610万m³
智能体：当前水位787.2m，库容约3610万m³，占兴利库容的84%。
```

**为什么必须用工具而不是RAG**：
- 大模型读曲线表做插值/计算，错误率很高（幻觉）
- 工具函数保证 **100%精确**，曲线计算、调洪试算这种必须精确
- 同理：调洪计算、溃坝流量、面积折算（1.23×柳林流量）都应做成工具

**应做成工具函数的数据清单**：
| 工具 | 数据来源 |
|-----|---------|
| 水位→库容查询 | 水位-库容查对表（1997实测） |
| 水位→泄量查询 | 水位-库容-泄流量关系表 |
| 调洪计算 | 不同频率洪水调洪成果表 |
| 洪水预报（面积比法） | Q_桃 = 1.23 × Q_柳 |
| 溃坝流量计算 | 堰流波流交汇法 |
| 预警级别判定 | 四级预警阈值表 |

### 喂法③：数据库 + 知识图谱 —— 用于"查实体关系"

**适用场景**：查"谁负责什么""哪个站测什么""险情关联什么措施"这类关系型问题。

**典型问题**：
- "高边坡滑坡该找哪个支队？负责人电话？"
- "柳林水文站测哪些项目？数据怎么共享？"
- "溢洪道1孔闸门故障，按预案归几级响应？"

**实现方式：结构化存为表/图**

**关系型数据库方式**（简单，推荐起步）：

```sql
-- 人员-职责-联系
CREATE TABLE emergency_personnel (
    name, role, team, phone, responsibility
);
-- 站点-观测项目
CREATE TABLE monitoring_stations (
    name, type, location, items, data_source
);
-- 险情-处置措施-所需物资
CREATE TABLE defect_measures (
    defect_type, measure, materials, personnel, steps
);
```

**知识图谱方式**（更强大，适合复杂推理）：

```
节点：高边坡滑坡(险情) ─处置→ 削坡减载(措施)
                         ─需要→ 挖掘机(物资)、3-5台(数量)
                         ─负责→ 第三支队/飞龙片(队伍)
                         ─触发→ 高水位+连阴雨(条件)
                         ─关联→ C级结构安全(鉴定结论)
```

**桃曲坡已有素材**：我之前生成的 `智能体映射分析.json` 已经是半成品知识图谱的结构化数据，可直接导入。

### 喂法④：规则引擎 / 系统提示词 —— 用于"固定规则判断"

**适用场景**：有明确if-then逻辑的判断，不该交给大模型"猜"。

**典型场景**：
- 水位>788m → 自动触发加密巡查
- 24h面雨量>260mm → Ⅰ级响应
- 险情上报：紧急情况1小时内上报

**实现方式A：硬编码规则（最可靠）**

```python
def determine_alert_level(rainfall_24h, inflow):
    if rainfall_24h > 260 or inflow > 3250:
        return "Ⅰ级"
    elif rainfall_24h > 190:
        return "Ⅱ级"
    elif rainfall_24h > 120:
        return "Ⅲ级"
    elif rainfall_24h > 60:
        return "Ⅳ级"
    return "正常"
```

**实现方式B：写进系统提示词（让大模型遵循流程）**

```
你是桃曲坡水库应急响应智能体。当用户报告险情时，按以下流程响应：
1. 判断险情类型（裂缝/渗漏/滑坡/管涌...）
2. 评估严重程度（一般/较大/重大/特别重大）
3. 确定响应级别（Ⅳ/Ⅲ/Ⅱ/Ⅰ）
4. 调用 get_measure 工具获取处置方案
5. 列出所需物资、人员、上报要求
始终引用预案条款作为依据。
```

## 三、各智能体的具体接入方案

| 智能体 | RAG文档检索 | 工具函数 | 结构化数据 | 规则/提示词 |
|--------|------------|---------|-----------|------------|
| **四预智能体** | 洪水预报方法说明、预报流程 | 洪水预报(面积比法)、水位预测、调洪计算 | 监测站网、雨量站 | 预警级别判定阈值 |
| **应急响应智能体** | 预案全文、处置步骤、组织职责 | 溃坝计算、物资查询、转移路线 | 抢险队伍、物资清单、人员联系 | 四级响应流程、上报时限 |
| **调度优化智能体** | 调度规程、调度原则 | 曲线查询、调洪计算、闸门开度 | 调度参数、特征水位 | 调度权限、汛限水位控制 |
| **安全评估智能体** | 安全鉴定报告、险情分析 | 溃坝模拟、风险计算 | 鉴定结论、缺陷清单 | 风险分级标准 |
| **智能巡检智能体** | 巡查内容、处置措施 | 缺陷查询、巡检任务生成 | 巡查路线、频次表、缺陷库 | 巡查频次触发规则 |
| **数据治理智能体** | 数据标准说明 | 数据校验、主数据查询 | 全部主数据实体 | 数据质量规则 |

## 四、推荐实施路线（务实三步走）

### 第一步（1-2周）：MVP——单智能体 + RAG
**目标**：先跑通一个"防汛知识问答"智能体，验证可行性。

1. 把《防洪抢险应急预案》《调度规程》切块 → 向量化 → 存向量库
2. 用现成框架搭一个RAG问答（LangChain / Dify / FastGPT）
3. 测试："管涌怎么处置？""Ⅰ级响应什么条件？"
4. **验证检索准确率，这是后续一切的基础**

> 💡 Dify/FastGPT 这类低代码平台能1天搭出原型，强烈建议先用它们验证，别一上来就写复杂代码。

### 第二步（1-2月）：接入结构化数据 + 工具
1. 水位-库容-泄流曲线做成查询API/工具函数
2. 主数据（队伍、物资、站点）入数据库
3. 智能体增加"工具调用"能力（function calling）
4. 从"只能查文字"升级到"能算数、查数据"

### 第三步（3-6月）：多智能体协同 + 数字孪生
1. 6个智能体各自建设，通过共享数据层协同
2. 接入实时监测数据（水位、雨量、闸位）
3. 与数字孪生3D平台联动
4. 实现预报-调度-应急一体化

## 六、最关键的3条经验

1. **精确数值绝不走RAG** —— 水位-库容-泄流曲线、调洪计算、阈值判断，必须做成工具函数/规则。大模型算数会出错，水利调度容不得这种错误。

2. **RAG的好坏70%取决于切块和元数据** —— 别用默认的"每500字硬切"。按预案的章节条款切，带上来源和主题标签，准确率天差地别。

3. **先验证检索质量，再谈智能体** —— 在投入做6个智能体之前，先确保"管涌处置"这个问题能准确召回预案第5.2.1节。检索不准，上层智能体全是空中楼阁。用低代码平台（Dify）1天就能验证。
