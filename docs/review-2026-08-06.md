# SmartTwinRes-skills 项目代码评审报告

**评审范围**：核心库（`lib/`）、supervisor 编排层、模型层（plan-generation/models）、查询脚本、测试代码
**评审日期**：2026-08-06
**项目性质**：技能驱动（SKILL.md）的多水库调度智能体集群，四场景闭环（A 暴雨/B 诊断/C 日常/D 应急）

---

## 总体评价

项目整体架构清晰：**租户身份 → 路径/过滤 → DAG 编排 → 子 skill 调用 → 仲裁/HITL → 报告** 的分层合理。代码注释充分（含中文注释），错误守卫意识强（arbitrator 大量 `isinstance` 守卫）。但存在几处**正确性缺陷**和**一致性问题**，按严重程度分类如下。

---

## 🔴 严重问题（影响正确性/安全）

### S1. `filters.apply_tenant_filter` 直接字符串拼接 `tid`，存在 SQL 注入隐患

`lib/filters.py:104` 用 f-string 把 `tid` 直接拼进 SQL。虽然 `tenant_id` 通常来自环境变量且为整数，但 `tenant_id` 参数是 `Optional[int]` 形参，调用方可传入任意值；一旦传入非整数字符串，SQL 语义会被破坏甚至注入。

```python
# 当前：f"{sql} AND tenant_id = {tid}"  -- 直接插值
```

**建议**：过滤函数不应直接拼值，应返回带占位符的 SQL + params，由 `execute_query` 参数化执行；或至少在拼接前 `int(tid)` 强制转换并校验范围。

### S2. `do_report` 场景 C 取 `sim` 用了 `stage_map["sim"]`，但 C 的 stagemap 中 `"sim": "step2"`，而 `_safe_load` 对未传 stage 安全。**真正的缺陷是**：`do_report` 第 349 行

```python
sim = _safe_load(stage_map["sim"]) or {}
```

当 `stage_map["sim"]` 为 `None`（场景 C 不存在该映射……实际 C 的 sim="step2" 是对的）。经核查 C 的 stage_map 是 `{"fc": "step1", "insp": None, "sim": "step2", "plan": None, "arb": None}`，逻辑可走通。**此项降级为提示**：`do_report` 对未知 scene 的默认 stage_map 假设 A 的 step 布局，若未来新增场景 E 而忘更新 stage_map，会静默取错阶段。建议未知 scene 时显式报错或返回空报告。

### S3. `execute_dag` 中 `status` 在子脚本执行失败时仍写入 State，但 **不会中断 DAG**

`supervisor/scripts/orchestrator.py:525-537`：子脚本 `out.get("ok")` 为 False 时 `status="error"`，但循环 `for stage in steps_to_run:` **继续执行下一阶段**，且最后无条件把事件标记为 `done`（L540）。

这意味着：forecasting 失败 → inspection 仍跑 → simulation 拿不到水位 → 仲裁拿到空数据 → 报告"数据不可用"，但事件状态是 `done`，运维 `replay` 不会把它列入待重放。

**影响**：失败的编排被掩盖为成功，违反"失败可见"原则。

**建议**：子脚本失败时 `break` 并把事件标记为 `error`/`failed`；或在仲裁前检查上游 stage 状态。

### S4. `run_stage_cmd` 超时后只返回 `{"ok": False, "stderr": str(e)}`，**未杀子进程**

`subprocess.run(..., timeout=60)` 超时会抛 `TimeoutExpired`，但 `subprocess.run` 在超时后**不会自动回收子进程**（Python 3.x 文档明确：调用方负责 `kill`）。被超时的子 skill（如连不上 DB 的 forecasting）会成为僵尸进程，长期运行下耗尽资源。

**建议**：改用 `subprocess.Popen` + `try/finally proc.kill()`，或在 `except TimeoutExpired` 中显式终止。

### S5. `lib/db._get_pool` 连接池对 `pymysql` 传了 `**DB_CONFIG`，其中 `charset`/`connect_timeout` 等是连接参数；但 `PooledDB` 的 `**DB_CONFIG` 会把 `cursorclass` 也传给池 creator（pymysql），而 `cursorclass` 又被显式传了一次（L74）。这在 `dbutils` 可用时可能因重复 kwarg 报 `TypeError`，或被静默吞掉。**需在真实带池环境验证**。

## 🟡 中等问题（健壮性/一致性）

### M1. `scene_router` 优先级设计有歧义：`DAILY_STRONG` 命中归 C，但 `EMERGENCY_STRONG` 命中归 D，二者无交叉词。问题是 `route()` L82 先判 `DAILY_STRONG`，若 trigger 同时含"每日"和"溃坝"，会归 C（漏报应急）。L76 的 `EMERGENCY_STRONG` 判断虽在前面，但 `EMERGENCY_STRONG` 与 `DAILY_STRONG` 是两次独立 `any()`，顺序正确。**实测逻辑成立**，但建议补单测覆盖"每日+溃坝"混合 trigger，防止后续改词表时回归。

### M2. `arbitrate_emergency` 的 `risk_level` 映射不完整

`supervisor/scripts/arbitrator.py:206-207`：

```python
"risk_level": "极高" if decision == "escalate" else ("高" if decision == "reject" else "中"),
```

但 `arbitrate_risk_levels` 支持四档（低/中/高/极高），这里却硬编码三档映射，且 `pending_approval` 一律"中"。当只有"仿真超汛限"（无告警无超泄）时，`decision=escalate`→`risk_level=极高`，这与"超汛限=高"的一般认知略有出入。建议明确文档化"应急场景一律从严升级"的语义。

### M3. `arbitrate_plan_vs_simulation` 规则1b（L80-90）有死代码

```python
if res.passed:
    res.passed = True  # 无意义
    res.suggestion = "建议启动更高一级响应或加大预泄"
```

`res.passed = True` 是冗余赋值（本就为 True 或已被前面设为 False）。若意图是"超汛限不否决但提示"，应改为 `if not res.passed: res.passed = True` 或直接只设 suggestion。当前写法在 `passed` 已为 False 时**不会**把它改回 True，suggestion 也只在 passed 为 True 时设置——逻辑与注释不符。

### M4. `do_arbitration` 场景 A 从 `sim` 取 `max_level` 的回退链不一致

`orchestrator.py:277-280`：

```python
sim_vals["max_level"] = sim_vals["max_level"] or sim.get("max_level") \
    or sim.get("highest_level")
sim_vals["max_discharge"] = sim_vals["max_discharge"] or sim.get("max_discharge") \
    or sim.get("discharge")
```

先用 `current_water_level` 数组算 max，再回退到 `sim.get("max_level")`。但 simulation full_context 通常只返回 `current_water_level` 数组，`max_level` 键可能不存在——回退链名不副实。建议统一 simulation 输出契约：要么总带 `max_level`，要么只消费 `current_water_level`。

### M5. `check_data_quality._iter_problems` 与 `_normalize_quality_dict` 双重阈值口径

- `_iter_problems`：水位过期 >24h → P0；降雨批次 >12h → P0；告警堆积 >500 → P1。
- `arbitrate_dam_diagnosis`：age >24 → 高；null_rate >50 → 高。

两套阈值在"24h"上一致，但 `_normalize_quality_dict` 把 `null_rate` 归一为百分比（0-100），而 `arbitrate_dam_diagnosis` L269 比较 `null_rate > 50`——口径一致（都是百分比）。**但** `check_water_level` SQL 返回的 `rz为空/总行数` 是 0-1 小数，`_normalize_quality_dict` 又 `*100`，而 arbitrator 比较的 `>50` 当成百分比——数字链路成立。建议在 docstring 明确"null_rate 单位为百分比 0-100"，避免后续误读为 0-1。

### M6. `supervisor_state._next_event_seq` 在并发 `new` 下可能生成重复 event_id

`supervisor_state.py:106-119`：先 `SELECT ... LIKE prefix%` 算 max_seq，再 INSERT。两个并发 `new` 会读到相同 max_seq，生成同一 event_id，第二个 INSERT 因 PRIMARY KEY 冲突报错。

单实例 SQLite + 短事务下概率低，但若未来多进程并发编排则会暴露。

**建议**：用 `INSERT ... ON CONFLICT(event_id) DO ...` 或在 events 表加 `seq` 列用 `AUTOINCREMENT`。

### M7. `supervisor_state._ensure_schema` 的 `ALTER TABLE` 补列无事务保护

`supervisor_state.py:96-98`：`PRAGMA table_info` 后若缺 `priority` 列则 `ALTER TABLE`。`_connect()` 每次连接都跑 `_ensure_schema`，在多进程同时首次连接时，两个进程可能同时 `ALTER`，第二个报 `duplicate column name`。

**建议**：`ALTER` 外包 `try/except sqlite3.OperationalError` 忽略"已存在列"错误。

## 🟢 轻微问题（可维护性/风格）

### L1. `lib/db.execute_query` 在 `fetchmany(cap+1)` 后，若结果正好等于 `cap+1` 行，`truncated=True` 且丢弃最后一行——正确。但 `MAX_ROWS=1000` 硬编码在模块级，调用方无法覆盖全局上限。建议从环境变量读 `SRM_DB_MAX_ROWS`。

### L2. `orchestrator.do_report` 中 `sim = _safe_load(stage_map["sim"]) or {}`（L349）取了 sim，但后续"三、推演与方案"段落用的是 `sim.get("current_water_level")`，而**plan 段落**（L418）只在 stage_map["plan"] 非空时加载 plan，却未在报告中输出 plan 的 `max_level/max_discharge`。报告"四、仲裁结论"引用了 arb，但 arb 在 do_arbitration 内联生成、未写回 stage_results——`do_report` 读 `stage_map["arb"]` 时取不到仲裁结果。**这是报告与仲裁的数据流断裂**：仲裁结果只返回给 orchestrator 打印，没落 State，do_report 自然取不到。建议 do_arbitration 把结果写入 stage_results，或 do_report 内联重算仲裁。

### L3. `plan-generation/models/dispatch_model.optimize_dispatch` 的水位超限补救（L154-162）在"加大泄流"后**未重新校验 `current_wl <= max_wl`**，可能仍超限；且 `extra_outflow` 计算用 `excess_cap * 10000 / 3600 / dt_hours`，单位换算（万m³→m³/s）需 `*10000/3600/dt`，正确。但该补救只在 `current_wl > max_wl` 时触发，**未处理 `current_wl < min_wl`**（水位过低）的情况——下泄不设下限可能导致水位跌破死水位。

### L4. `forecasting/scripts/query_forecast_data.py` 中 `query_flood_limit` 与 `_pick_in_season_flse_lim` 的汛期匹配逻辑（`flood_season_start <= today_md AND flood_season_end >= today_md`）在跨年汛期（如 11 月到次年 3 月）会失配。若水库汛期跨年需另行处理。

### L5. 多处 `sys.path.insert(0, ...)` 重复插入且未去重，长期运行下 `sys.path` 会膨胀。建议封装一个 `_ensure_path(p)` 工具。

### L6. `tests/integration/test_supervisor_e2e.py` 的 `_TempState` 用 `importlib.reload(supervisor_state)` 重载模块以重新读 `SRM_STATE_DIR`，但 `orchestrator` 模块内的 `_connect` 引用的是 `supervisor_state._connect`，reload 后引用关系需重新绑定——当前测试通过 `import orchestrator` 后 `orchestrator._connect()` 取的是 reload 后的函数，逻辑成立。但 reload 模式脆弱，建议改为 `monkeypatch SRM_STATE_DIR` + 显式 connect。

### L7. `lib/tenant.current_tenant_id` 对 `SRM_TENANT_ID="0"` 会返回 0（合法），但对 `"  18  "` 会 `int("18")=18`——正确。然而 `DEFAULT_TENANT_ID=18` 是三岔水库硬编码，若部署到新水库忘设 `SRM_TENANT_ID`，会静默查到三岔的数据。建议在 `DEFAULT_TENANT_ID` 命中时打印一条 stderr 警告。

## ✅ 值得肯定之处

1. **租户隔离设计扎实**：`lib/tenant.py` 单一入口 + `lib/filters.py` 表驱动过滤，避免了业务代码硬编码 `tenant_id=18`。注释明确说明了默认值的来源。
2. **仲裁守卫完备**：`arbitrate_dam_diagnosis` / `arbitrate_emergency` 对 None、非 dict、非数值输入都有 `isinstance` + `try/except` 兜底，单测 `test_robust_to_none_inputs` 覆盖到位。
3. **凭据安全**：`lib/db._require_env` 强制环境变量读 DB 口令，杜绝硬编码；`DB_CONFIG` 双命名空间（SRM/POWERELF）降级回退设计合理。
4. **HITL 检查点**：`execute_dag` 在仲裁阶段前 `UPDATE events SET status='awaiting_approval'` 并提示 `--approve` 续跑，人机协同边界清晰。
5. **断点续跑**：`supervisor_state.cmd_resume` + `DAG_ORDER` 实现"已完成 stage 集合 diff 待跑"，状态机设计干净。
6. **测试覆盖核心路径**：`test_arbitrator.py` 覆盖四场景仲裁的 正常/边界/异常档；`test_supervisor_e2e.py` 用临时 SQLite State 做端到端注入断言，不依赖真 DB。

## 修复优先级建议

| 优先级 | 问题 | 建议动作 |
|--------|------|----------|
| P0 | S3 子脚本失败仍标记 done | 失败时 break + 事件标 error |
| P0 | S4 超时未杀子进程 | 改 Popen + finally kill |
| P1 | S1 tenant_id 字符串拼接 | 改参数化或 int 强转 |
| P1 | L2 仲裁结果未落 State，报告取不到 | do_arbitration 写回 stage_results |
| P1 | M3 arbitrate_plan_vs_simulation 死代码 | 清理 if res.passed 冗余赋值 |
| P2 | M6/M7 并发 event_id / ALTER 列 | ON CONFLICT 或 try/except |
| P2 | L3 dispatch 水位跌破死水位未处理 | 加 min_wl 下泄下限 |
| P3 | L4 跨年汛期失配 | 视水库汛期是否跨年决定是否处理 |
| P3 | L7 默认 tenant 静默命中三岔 | 命中默认值时 stderr 警告 |

---

**结论**：项目在"技能编排 + 多水库隔离 + 仲裁 HITL"层面的设计成熟度高，核心数据流（forecasting → simulation → plan → 仲裁 → 报告）闭环完整。主要风险集中在**失败可见性**（S3/S4）和**数据流断裂**（L2 仲裁未落 State、M3 死代码）。建议优先修复 P0/P1 项，其余可纳入后续迭代。
