> **评审范围**: 全仓只读评审（未改动任何代码）。覆盖 `lib/` 共享层、DB 安全、supervisor 编排、5 个领域 skill 脚本、eval 框架与测试。

## 一、总体评价

这是一个**设计严谨、工程纪律良好**的水库"四预"+诊断+编排 skill 集合。代码风格统一（中文注释/Conventional Commits），安全红线在多数地方被认真遵守——参数化查询占绝对多数、`%%` 转义已被正确修复、tenant 身份有单一真相源、eval 框架分层清晰且 CI 友好（无 DB/无 hermes 依赖）。supervisor 的 DAG+断点续跑+HITL+仲裁四件套是真实可用的高价值骨架。

但评审也发现若干**与项目自己定下的红线相悖**的残留点，以及一类**跨模块一致性裂缝**。按"安全合规 > 一致性/漂移 > 卫生 > 可测性"排序如下。

## 二、安全与合规类（最高优先级）

### S1. `lib/db.py:execute_write` —— 只读原则的实质违反
**位置**: `lib/db.py:269-290`

```python
def execute_write(sql, params=None):
    conn = get_connection()
    try:
        with conn.cursor() as cursor:
            rows = cursor.execute(sql, params)
            conn.commit()          # ← commit
            return rows
    except Exception:
        conn.rollback()            # ← rollback
        raise
    finally:
        conn.close()
```

**问题**: 共享 DB 层导出了带 `commit()`/`rollback()` 的写能力，与全项目"只读查询"原则直接冲突。虽然目前**没有任何调用方**使用它（grep 无引用），但它的存在本身就是一道敞开的门——任何 LLM 生成的脚本 `from lib.db import execute_write` 即可获得对生产库的写/删权限。

**建议**: 删除 `execute_write`。若将来确有写入需求，应放在独立、显式受控的写通道，而非只读共享层。**删除前先 `grep -rn execute_write` 二次确认零引用**（本次评审已确认无引用）。

### S2. `lib/filters.py` 的 tenant 过滤用 f-string 拼接 —— 与"仅参数化"红线不一致
**位置**: `lib/filters.py:120`（及 `generate_where_clause` 同模式）

```python
return f"{sql} AND tenant_id = {tid}"
```

**问题**: `tid` 虽在调用前经 `int()` 校验（构成注入防护），但这种"先拼字符串、靠校验兜底"的写法，与项目规则"参数化 `%s` 占位符，禁止字符串拼接用户值进 SQL"在精神上相悖。它把"防注入"的成败押在"上游每次都记得做 int 校验"上，一旦有路径漏校验即破防。而仓库里其余 16+ 处 tenant 过滤全部走 `tenant_id = %s` + params——**这是唯一偏离规范的一处**。

**建议**: `apply_tenant_filter` / `generate_where_clause` 改为返回 `(sql_suffix, params)` 二元组，或在调用点用 `%s` 占位。消除"靠校验兜底的拼接"这一反模式，让规则零例外。

### S3. 告警表 `ew_info_message` 跨 skill 均不做 tenant 过滤
**位置**:
- `early-warning/scripts/query_early_warning.py` —— 12 个告警查询函数（`query_unconfirmed` / `query_by_level` / `query_recent` / `query_high_level` / `query_alarm_trend` 等）**全部无 `tenant_id` WHERE**；全脚本仅 5 处 `tenant_id` 引用，全集中在 `query_water_level`/`query_rainfall`（st_rsvr_r/st_pptn_r）。
- `diagnosis-verification/scripts/check_data_quality.py:check_alerts` —— `ew_info_message` 同样无 tenant 过滤。
- `supervisor/scripts/supervisor_state.py:cmd_health` —— 告警堆积查询 `WHERE deleted=0 AND message_confirm=0`，无 tenant。

**定性**: 这是**有意的设计选择**，`lib/filters.py` 明确标注 `ew_info_message = filter:False`（"告警跨租户,不强制"）。所以不是 bug，而是**一个未被充分论证的隔离缺口**：在三岔(18)/桃曲坡(20)多水库共库部署下，A 水库的告警会出现在 B 水库的 early-warning/supervisor 视图里。`query_high_level` 的输出直接喂给 `arbitrate_emergency`（场景 D 仲裁），意味着**A 库的高级告警可能抬高 B 库的应急风险判定**。

**建议**: 若业务确需"告警全库可见"（例如告警本身已带水库语义、或中央调度需全局视角），则在 SKILL.md/db-config.md 显式记录这一决策与影响面；若不需要，则补 `tenant_id = %s`。**关键是把"当前行为"从隐性默认升级为显式决策**。

### S4. 同一张 `f_rnfl_h` 表，forecasting 与 plan-generation 的 tenant 处理不一致
**位置**:
- `plan-generation/scripts/query_plan_data.py:query_rainfall_forecast` —— 主查询 + `fymdh` 子查询**均按 tenant 过滤**（注释确认经 live DESCRIBE，f_rnfl_h 有 `tenant_id` 列）。
- `forecasting/scripts/query_forecast_data.py:query_rainfall_forecast` —— **无 tenant 过滤**（代码注释自述"无 tenant"）。

**问题**: 同一张表、同一个字段、两个 skill 给出相反结论。memory 也记录"f_rnfl_h HAS tenant_id（leak fixed 2026-08-10）"——说明**曾经发生过跨租户泄漏并被修复**，但修复只落到了 plan-generation 一侧，forecasting 仍是泄漏的旧形态。这是 S3 之外另一处真实的多租户隔离风险：forecasting 读到的"未来预报"可能混入他库数据。

**建议**: 以 live schema 为准统一两处。f_rnfl_h 既然有 `tenant_id`，forecasting 应补 `tenant_id = %s`。这同时修复了 `cmd_health` 对 `f_rnfl_h` 的未来预报覆盖统计（当前已按 tenant 过滤，是正确的——侧面印证 forecasting 脚本的"无 tenant"注释已过时）。

### S5. simulation 的 `srm_flood_history_result` 系列查询无 tenant 过滤
**位置**: `simulation/scripts/query_simulation_data.py` —— `query_flood_detail`/`query_flood_result`/`query_flood_result_curve`/`query_flood_inflow`/`query_flood_statistics` 按 `flood_id` 查 `srm_flood_history_result`，**无 `tenant_id`**。

**缓解**: `flood_id` 来自 `query_historical_floods`（tenant 过滤过的 `srm_flood_history_base`），属"间接隔离"。

**风险**: 一旦 `flood_id` 经 LLM 之手从别的途径传入（如用户 prompt 指定历史洪水名），隔离即被旁路。属于**纵深防御缺口**，非即时 bug。

**建议**: 若该表有 `tenant_id` 列，补防御性 `AND tenant_id = %s`（与 historical_floods 同 tenant）；无该列则在 db-config.md 记录"依赖 flood_id 间接隔离"。

## 三、一致性与漂移类

### C1. `eval/lib/truth.py` 复制 lib/db.py 连接逻辑，且默认更弱
**位置**: `eval/lib/truth.py:17-28`（`_connect`）

**问题**: live_db 真值查询绕开 `lib/db.py`，自写 `pymysql.connect`，且默认值更宽松——`user` 默认 `"root"`、`password` 默认 `""`，比 `lib/db.py` 的 `_require_env`（fail-loud）**弱**。两套连接逻辑必然漂移：lib 层改了超时/charset/连接池策略，eval 不会跟进。

**建议**: truth.py 改为复用 `lib.db.get_connection()`（或至少复用其 `_ensure_db_config` 读到的同一组 env 默认），消除双份连接逻辑与"eval 默认空密码"这一隐患。

### C2. 三种汛限水位查询实现并存
**位置**:
- plan-generation: `DATE_FORMAT(NOW(), '%%m%%d')` 在 SQL 侧做汛期区间匹配（已修 `%%` 转义 bug）。
- simulation: `datetime.now().strftime("%m%d")` 在 Python 侧算出 `today_md`，作为 `%s` 参数传入。
- forecasting: `_pick_in_season_flse_lim` 用 Python 侧 `today_mmdd` 做区间比较（未见跨年处理）。

**问题**: 同一业务概念（"今天是否在汛期、取对应汛限"）有三套实现，行为细节（跨年、空数据兜底）各异。这是维护期最高频出错的形态——改一处忘改另两处。

**建议**: 抽到 `lib/` 一个 `current_flood_limit(tenant_id)` 单一实现，三个 skill 共享。plan-generation 的 `%%` 修复证明这块逻辑脆弱且易错，统一是治本。

### C3. supervisor 的 `asdict` 再导出耦合 + 内联 `_ensure_path`
**位置**: `supervisor/scripts/orchestrator.py`（`from arbitrator import asdict`）、`arbitrator.py` 与 `orchestrator.py` 各自内联 `_ensure_path`。

**问题**: orchestrator 从 arbitrator 再导出 `asdict`（标准库 `dataclasses.asdict` 的再导出），形成模块间隐性耦合——arbitrator 的 import 表变动会波及 orchestrator 的可用符号。两文件各自内联 `_ensure_path` 而非用 `lib.paths.ensure_path`，注释称"lib.paths 会触发 lib.db 凭据检查"——但 `lib/db.py` 已改为惰性 `_ensure_db_config()`（import 不再 sys.exit），**该理由已失效**，内联属于过时代码。

**建议**: orchestrator 直接 `from dataclasses import asdict`；两文件改用 `lib.paths.ensure_path`。顺手验证惰性配置确实消除了旧顾虑。

## 五、可测性类

### T1. `cmd_health` 导入 `lib.db`/`lib.tenant`，破坏 supervisor 的无 DB 可测性
**位置**: `supervisor/scripts/supervisor_state.py:cmd_health`

**问题**: supervisor_state.py 的其余命令（new/set/get/resume/stats/replay）纯 SQLite、零外部依赖，是 CI 无 DB 环境可测的。唯独 `cmd_health` 在函数体内 `from lib.db import ...` + `from lib.tenant import ...`，一旦测试触发该路径即需要真实 MySQL + env，与"supervisor 状态层应可在无 DB 下单测"的设计意图冲突。

**建议**: 将 `cmd_health` 的"查 DB 取原始数据"与"健康判定"拆分——判定逻辑纯函数、可单测；DB 查询作为可注入的 query_fn。这也是 `cmd_health` 语义上更接近"运维探针"而非"状态持久化"的信号，可考虑独立成 `supervisor/scripts/health_check.py`。

### T2. 模块级 `TENANT = current_tenant_id()` 锁定导入时刻身份
**位置**: `inspection_check.py:37`、`check_data_quality.py`（`TENANT = current_tenant_id()`）、`query_plan_data.py:20`（`DEFAULT_TENANT`）。

**问题**: tenant 在 **import 时**解析并冻结。CLI 模式下 `--tenant` 在 `query_plan_data.py` 里靠"先 `os.environ['SRM_TENANT_ID']=...` 再调用函数、函数内 `resolve_tenant()` 重读"绕过（正确），但 `inspection_check.py`/`check_data_quality.py` 用的是模块级 `TENANT` 常量直接进 SQL——**`--tenant` 覆盖对它们无效**（inspection_check 甚至没有 `--tenant` 参数）。作为 CLI 尚可（每次进程重解析），但被 import 复用时身份不可变，是潜在陷阱。

**建议**: 统一为"函数内 `resolve_tenant()` 动态解析"模式（plan-generation 已是范本），移除模块级 `TENANT` 常量，或至少给 inspection_check 补 `--tenant`。
