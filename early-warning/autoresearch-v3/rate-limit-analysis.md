## 限流原因分析

### 1. 并发请求过多

测试脚本在短时间内发送多个请求，触发了API网关的限流机制。

```
请求间隔: 10-15秒
API限制: 可能是每分钟N个请求
```

### 2. Token消耗过大

某些复杂问题需要较长的上下文，导致token消耗较大：
- 平均token数: ~23,368
- 复杂问题可能需要更多token

### 3. API网关限流

`http://127.0.0.1:7171/_h/hermes/upstreams/xiaomi` 是一个代理网关，可能有：
- 每分钟请求限制
- 每小时请求限制
- 并发连接限制

## 解决方案

### 方案1: 增加请求间隔

将测试间隔从10-15秒增加到30-60秒。

```bash
# 原来的间隔
sleep 10

# 建议的间隔
sleep 30  # 或 sleep 60
```

### 方案2: 使用不同的API密钥

如果有多个API密钥，可以轮换使用。

### 方案3: 调整API网关配置

如果可以控制API网关，可以：
- 增加速率限制
- 增加并发连接数
- 调整限流策略

### 方案4: 分批测试

将测试分成多个批次，每批次之间休息更长时间。

```bash
# 批次1: Q62-Q69 (8题)
# 休息5分钟
# 批次2: Q70-Q77 (8题)
# 休息5分钟
# 批次3: Q78-Q85 (8题)
# ...
```

### 方案5: 使用本地模型

如果可能，使用本地部署的模型，避免API限流。

## 实际解决过程

在测试过程中，我们采取了以下措施：

1. **增加测试间隔**: 从3秒增加到10-15秒
2. **分批测试**: 每次测试5-8题
3. **逐个重试**: 失败的测试单独重试，间隔20-30秒
4. **等待后重试**: 遇到限流后等待60秒再重试

通过这些措施，大部分测试都成功完成了。只有6个测试因为限流过于严格而最终失败。
