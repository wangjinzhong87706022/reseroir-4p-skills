# diagnose（诊断）— 8 阶段详细文档

## Phase 0：澄清确认

### 目的
确认诊断范围和时间边界，避免分析错误时间段或遗漏影响范围。

### 执行步骤
1. 确认问题类型（数据异常/告警误报/预案失败/系统错误）
2. 确认时间范围（最近 1 小时/今天/本周/历史对比）
3. 确认影响范围（单个 skill/跨 skill/全系统）
4. 确认优先级（P0 紧急/P1 高优/P2 普通）

### 输出格式
```
【Phase 0 完成】
- 问题类型：<分类>
- 时间范围：<起止时间>
- 影响范围：<涉及 skill/模块>
- 优先级：<P0/P1/P2>
- 下一步：进入 Phase 1 全景扫描
```

### 为什么不能跳
- 不确认时间范围就会分析错误时间段
- 不确认影响范围就会遗漏跨 skill 关联问题

---

## Phase 1：全景扫描

### 目的
收集全量数据，统计错误分布，为后续分析提供全局视图。

### 执行步骤
1. **数据源检查**：验证数据是否来自正确的 query 脚本
2. **错误统计**：按类型、级别、测站统计错误数量
3. **状态检查**：检查各 skill 输出是否满足验收标准

### 数据源对照表
| Skill | 正确数据源 | 验证方式 |
|-------|----------|---------|
| forecasting | `query_forecast_data.py` | 检查输出是否包含"数据来源：query_forecast_data.py" |
| early-warning | `query_early_warning.py` | 检查输出是否包含"数据来源：query_early_warning.py" |
| plan-generation | `query_plan_data.py` | 检查输出是否包含"数据来源：query_plan_data.py" |
| simulation | `query_simulation_data.py` | 检查输出是否包含"数据来源：query_simulation_data.py" |

### 输出格式
```
【Phase 1 完成】
- 数据源：<来源脚本>（✅ 正确 / ❌ 混用其他 skill 数据源）
- 错误统计：<总数> 条（<分类>）
  - 数据不足：<N> 条
  - 精度待评定：<N> 条
  - 参数硬编码：<N> 条
  - 格式错误：<N> 条
- 状态检查：<P0/P1/P2> 不通过项数
```

### 为什么不能跳
- 不扫全景就会遗漏类别
- 不知道错误分布就无法识别突增/慢性/回归模式

---

## Phase 2：数据质量检查

### 目的
识别数据问题（缺失、异常、过时），评估数据质量。

### 检查维度

#### 1. 完整性检查
- 数据覆盖率（实际数据 / 应有数据）
- 缺失率（缺失数据 / 应有数据）
- 关键字段缺失率（如 rz 为空率）

#### 2. 准确性检查
- 数值范围是否合理（水位 ~450-465m、降雨 0-500mm）
- 时间戳是否连续（无断层、无未来时间）
- 外键关联是否完整（stcd、测站编码）

#### 3. 时效性检查
- **数据新鲜度标准**：

| 数据类型 | 最大允许延迟 | 超时处理 |
|---------|------------|---------|
| 水位 | 1 小时 | 立即告警 |
| 降雨预报 | 6 小时 | 标记"陈旧预报" |
| 告警 | 24 小时 | 升级人工 |

### 数据质量评级

| 评级 | 标准 | 处理建议 |
|------|------|---------|
| **优** | 完整率 >95%、准确率 100%、新鲜度达标 | 正常使用 |
| **良** | 完整率 80-95%、少量异常、新鲜度基本达标 | 可用，需监控 |
| **中** | 完整率 50-80%、部分异常、部分过期 | 谨慎使用，标记风险 |
| **差** | 完整率 <50%、大量异常、严重过期 | **不可用，立即修复数据源** |

### 输出格式
```
【Phase 2 完成】
- 完整性：<评分>（缺失率 <X>%）
- 准确性：<异常数量> 条（<举例>）
- 时效性：<过期数据数量> 条（<举例>）
- 数据质量评级：<优/良/中/差>
```

## Phase 3：异常详情

### 目的
提取完整的错误上下文（traceback + 输入参数），为根因分析提供证据。

### 执行步骤
1. **提取完整 traceback**：
   - 错误堆栈（从顶层到根因）
   - 错误码（HTTP/数据库/业务逻辑）

2. **截取输入参数**：
   - SQL 语句及参数
   - API 请求及响应
   - 触发条件（时间、测站、阈值）

3. **历史对比（git log 交叉验证）**：
   - 首次出现时间
   - 最近代码变更（最近 7 天 commit）
   - 历史同类问题及解决方案

### 输出格式
```
【Phase 3 完成】
- 错误类型：<分类>
- 完整 traceback：<堆栈信息>
- 输入参数：<SQL/API 请求>
- 首次出现：<时间>（<git commit hash>）
- 历史同类问题：<有/无>（若有，<解决方案链接>）
```

### 为什么不能跳
- 不截取完整 traceback 就定位不了根因
- 不做 git log 交叉验证就无法区分"新问题"还是"老毛病突然恶化"

## Phase 4：关联分析

### 目的
跨域关联分析，识别复合问题（多个问题同时出现，相互影响）。

### 分析维度

#### 1. 水位 × 降雨 × 渗流关联
- 同时触发水位和降雨告警 → 大坝风险？
- 渗流异常 + 水位上升 → 渗透破坏风险？

#### 2. 跨 skill 关联
- forecasting 精度待评定 → early-warning 告警误报？
- plan-generation 方案超限 → simulation 预演失败？

#### 3. 时间序列关联
- 多个错误是否在同一时间窗口出现？
- 是否有先后依赖关系（A 导致 B）？

### 关联度评级

| 评级 | 标准 | 处理建议 |
|------|------|---------|
| **高** | 多个维度同时异常，时间窗口重合 | 系统性故障，优先处理 |
| **中** | 部分维度异常，有关联但非同时 | 需综合分析，制定综合方案 |
| **低** | 孤立问题，无明显关联 | 单独处理 |

### 输出格式
```
【Phase 4 完成】
- 跨域关联：<水位+降雨+渗流 同时异常？>
- 跨 skill 关联：<涉及哪些 skill，依赖关系>
- 时间关联：<是否同时出现，先后顺序>
- 关联度评级：<高/中/低>
```

## Phase 5：根因分析

### 目的
6 类根因分类 + 证据链推理，避免猜测。

### 6 类根因分类

| 分类 | 特征 | 修复方向 |
|------|------|---------|
| **外部系统异常** | MCP 工具返回 Java stackTrace | try-except + fallback + retry |
| **内部代码缺陷** | TypeError/AttributeError 在 src/ | 精确修改 file:line |
| **数据问题** | 用户数据异常、表不存在 | 不修，转工单给 Owner |
| **基础设施问题** | 连接池超时、网络波动 | 配置调整（pool_size=10） |
| **LLM/模型异常** | 幻觉、编造不存在的表名 | Prompt 约束 + schema 校验 |
| **预期行为（误报）** | 确认后降级日志级别 | 合理降级（非掩盖故障） |

### 证据链格式

```
[事实] <观测到的事实>
[推理] <推导过程>
[结论] <根因结论>
```

**示例**：
```
[事实] 水位数据连续 3 小时未更新（最近时间 2026-07-10 08:00）
[推理] 数据库连接池可能超时，导致查询失败
[结论] 基础设施问题 → 调整连接池配置
```

### 区分"掩盖故障"和"合理降级"

| 行为 | 类型 | 判断标准 |
|------|------|---------|
| 把 `logger.error` 改成 `logger.warning`，错误还在但不再上报 | ❌ 掩盖故障 | 错误未解决，只是不报了 |
| 降级为非实时数据源，并记录降级日志供后续排查 | ✅ 合理降级 | 有 fallback 机制，错误可追溯 |

## Phase 6：影响评估

### 目的
评估问题的影响范围和严重程度，确定修复优先级。

### 评估维度

#### 1. 影响范围
- 涉及哪些 skill/module
- 影响哪些用户/场景
- 是否影响下游系统

#### 2. 严重程度

| 级别 | 标准 | 响应时间 |
|------|------|---------|
| **P0** | 系统不可用、数据丢失、安全风险 | 立即（<1 小时） |
| **P1** | 核心功能异常、性能下降 >50% | 今日（<24 小时） |
| **P2** | 边缘功能异常、性能下降 <50% | 本周（<7 天） |

#### 3. 紧迫性
- 是否在汛期/防洪关键期
- 是否影响调度决策
- 是否有时间窗口修复

---

## Phase 7：修复建议

### 目的
输出短期止血 + 长期根治方案，明确优先级。

### 修复原则

1. **短期止血**（立即执行，<1 小时）：
   - 临时绕过问题（如切换到备用数据源）
   - 降级处理（如关闭非核心功能）
   - 手动修复（如调整参数、重启服务）

2. **长期根治**（本周内完成）：
   - 修复代码缺陷（精确到 file:line）
   - 优化数据质量（补全缺失数据、修正错误数据）
   - 增强系统鲁棒性（增加重试、熔断、降级机制）

### 输出格式
```
【Phase 7 完成】
【短期止血】
- 方案 1：<临时绕过>（预计时间：<X> 分钟）
- 方案 2：<降级处理>（预计时间：<Y> 分钟）

【长期根治】
- 方案 1：<修复代码>（file:line，预计时间：<X> 小时）
- 方案 2：<优化数据>（预计时间：<Y> 小时）

【优先级】
- P0：<立即执行>（<原因>）
- P1：<今日修复>（<原因>）
- P2：<本周修复>（<原因>）
```

## Phase 8：知识沉淀

### 目的
将诊断结果写入知识库，避免同类问题重复排查。

### 执行步骤

#### 1. 写入知识库

```yaml
# state/knowledge-base/root-cause-solutions.yaml
- problem_type: <问题类型>
  root_cause: <根因>
  evidence: <关键证据>
  solution: <解决方案>
  fix_time: "首次 <X> 分钟 → 有知识库后 <Y> 分钟"
  tags: [<标签>]
  success_rate: 0.95
  last_used: "2026-07-10"
```

#### 2. 更新监控规则

```yaml
# state/infrastructure-config/alert-rules.yaml
- rule_name: <规则名称>
  condition: <触发条件>
  severity: <P0/P1/P2>
  action: <处理动作>
```

#### 3. 复利效应

| 问题类型 | 首次修复时间 | 有知识库后 |
|---------|------------|----------|
| 水位数据超时 | 48 分钟 | **15 分钟** |
| 告警风暴 | 30 分钟 | **10 分钟** |
| 参数硬编码 | 10 分钟 | **5 分钟** |

| 问题类型 | 典型表现 | Phase 5 根因分类 |

| 数据源混用 | 水位 240m（应为 460m） | 内部代码缺陷 |
