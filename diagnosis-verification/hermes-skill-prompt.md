# Hermes Agent 诊断工作流 Prompt 模板

## 使用说明

在 Hermes Agent 对话中，将此文件作为 Skill 加载：

```
@/home/scada/SmartTwinRes20260601/SmartTwinRes-skills/diagnosis-verification/hermes-skill-prompt.md
```

然后按工作流执行诊断。

---

## 工作流 1：完整诊断（8 Phase）

### 输入

用户报告问题，例如：
- "水位数据异常，连续 3 小时未更新"
- "告警堆积，最近有大量未确认告警"
- "预报数据有问题，精度待评定"

### 执行步骤

#### Phase 0：澄清确认

**请确认以下信息**：
1. **问题类型**：数据异常 / 告警误报 / 预案失败 / 系统错误
2. **时间范围**：最近 1 小时 / 今天 / 本周 / 历史对比
3. **影响范围**：单个 skill / 跨 skill / 全系统
4. **优先级**：P0 紧急 / P1 高优 / P2 普通

**输出格式**：
```
【Phase 0 完成】
- 问题类型：<分类>
- 时间范围：<起止时间>
- 影响范围：<涉及 skill/模块>
- 优先级：<P0/P1/P2>
```

---

#### Phase 1：全景扫描

**执行数据源检查**：
```bash
# 根据问题类型选择对应的查询脚本
python3 <skill_dir>/scripts/query_<skill>_data.py --type <type>
```

**数据源对照表**：
| Skill | 查询脚本 | 常见查询类型 |
|-------|---------|------------|
| forecasting | query_forecast_data.py | current_water_level, rainfall_forecast, flood_limit |
| early-warning | query_early_warning.py | unconfirmed, by_level, recent |
| plan-generation | query_plan_data.py | current_water_level, flood_limit |
| simulation | query_simulation_data.py | full_context, flood_detail |

**统计错误分布**：按类型、级别、测站分类统计

**输出格式**：
```
【Phase 1 完成】
- 数据源：<脚本名>（✅ 正确 / ❌ 混用）
- 错误统计：<总数> 条（<分类>）
```

---

#### Phase 2：数据质量检查

**检查维度**：
1. **完整性**：数据覆盖率、缺失率
2. **准确性**：数值范围（水位 ~450-465m）、时间戳连续性
3. **时效性**：
   - 水位：< 1 小时
   - 降雨预报：< 6 小时
   - 告警：< 24 小时

**数据质量评级**：优（>95%）/ 良（80-95%）/ 中（50-80%）/ 差（<50%）

**输出格式**：
```
【Phase 2 完成】
- 完整性：<评分>（缺失率 <X>%）
- 准确性：<异常数> 条
- 时效性：<过期数> 条
- 数据质量评级：<优/良/中/差>
```

---

#### Phase 3：异常详情

**提取**：
1. 完整 traceback（错误堆栈）
2. 输入参数（SQL、API 请求）
3. **git log 交叉验证**（最近 7 天 commit）

**输出格式**：
```
【Phase 3 完成】
- 错误类型：<分类>
- 首次出现：<时间>（<git commit hash>）
- 历史同类问题：<有/无>
```

---

#### Phase 4：关联分析

**分析维度**：
1. **跨域关联**：水位 × 降雨 × 渗流
2. **跨 skill 关联**：forecasting → early-warning → plan-generation
3. **时间序列关联**：多错误是否同时出现

**关联度评级**：高 / 中 / 低

**输出格式**：
```
【Phase 4 完成】
- 跨域关联：<是否同时异常>
- 跨 skill 关联：<涉及哪些 skill>
- 关联度评级：<高/中/低>
```

---

#### Phase 5：根因分析

**6 类根因分类**：
| 分类 | 特征 | 修复方向 |
|------|------|---------|
| 外部系统异常 | Java stackTrace | try-except + fallback |
| 内部代码缺陷 | TypeError/AttributeError | 精确修改 file:line |
| 数据问题 | 数据异常、表不存在 | 转工单 |
| 基础设施问题 | 连接池超时 | 配置调整 |
| LLM/模型异常 | 幻觉、编造表名 | Prompt 约束 |
| 预期行为（误报） | 确认后降级 | 合理降级（非掩盖） |

**证据链格式**：
```
[事实] <观测到的事实>
[推理] <推导过程>
[结论] <根因结论>
```

**输出格式**：
```
【Phase 5 完成】
- 根因分类：<6 类之一>
- 证据链：
  [事实] ...
  [推理] ...
  [结论] ...
```

---

#### Phase 6：影响评估

**评估维度**：
1. **影响范围**：涉及哪些 skill/module
2. **严重程度**：P0 / P1 / P2
3. **紧迫性**：是否在汛期/关键期

**输出格式**：
```
【Phase 6 完成】
- 影响范围：<描述>
- 严重程度：<P0/P1/P2>
- 紧迫性：<高/中/低>
```

---

#### Phase 7：修复建议

**短期止血**（<1 小时）：临时绕过或降级
**长期根治**（本周）：修复根因
**优先级**：P0 立即 / P1 今日 / P2 本周

**输出格式**：
```
【Phase 7 完成】
【短期止血】
- 方案 1：<描述>（<时间>）
【长期根治】
- 方案 1：<描述>（<时间>）
【优先级】
- P0：<方案>（<原因>）
```

---

#### Phase 8：知识沉淀

**写入知识库**（knowledge-base/root-cause-solutions.yaml）：
```yaml
- problem_type: <问题类型>
  root_cause: <根因>
  evidence: <关键证据>
  solution: <解决方案>
  fix_time: "首次 <X> 分钟 → 有知识库后 <Y> 分钟"
  tags: [<标签>]
```

**更新监控规则**（infrastructure-config/alert-rules.yaml）

**输出格式**：
```
【Phase 8 完成】
- 知识库：已写入 <N> 条
- 监控规则：已更新 <N> 条
- 下次预计：<X> 分钟（首次 <Y> 分钟）
```

## 工作流 2：输出验证（6 Layer）

### 输入

预报/预警/预案/预演的输出内容

### 执行 6 层验证

#### Layer 1：数据源验证
- ✅ 数据来自正确的 query 脚本
- ✅ 无 skill 混用

#### Layer 2：格式规范验证
- ✅ 三段式完整
- ✅ 引用规范准确
- ✅ 参数无硬编码

#### Layer 3：业务规则验证
- ✅ 数值在合理范围
- ✅ 计算正确

#### Layer 4：安全约束验证
- ✅ 水位未超汛限（<100%）
- ✅ 下泄量未超下游安全泄量

#### Layer 5：跨域一致性验证
- ✅ 多 skill 数据一致

#### Layer 6：法规符合性验证
- ✅ 引用现行有效规范

**输出格式**：
```
【验证报告】
| 层级 | 验证内容 | 结果 |
|------|---------|------|
| Layer 1 | 数据源验证 | ✅/❌ |
| Layer 2 | 格式规范验证 | ✅/❌ |
...
总评：<通过/不通过>
```

## 工作流 3：自动修复（6 Step）

### 前置条件

1. ✅ diagnose 已完成（8 Phase）
2. ✅ verify 已验证诊断结果
3. ✅ 根因分类明确

### 执行 6 步

#### Step 1：解析诊断报告
提取根因、修复建议、受影响文件

#### Step 2：查询知识库
匹配历史解决方案，复用经验

#### Step 3：生成修复方案
根据 6 类根因选择修复模式

#### Step 4：生成修复补丁
生成 diff 格式补丁

#### Step 5：执行测试
单元 + 集成 + 回归 + 性能
**最多 3 轮重试**

#### Step 6：提交并部署
创建分支 → 提交 PR → 触发预发部署

## 常见场景速查

| 场景 | 触发条件 | 关键检查点 |
|------|---------|-----------|
| **水位数据超时** | 数据 >1 小时未更新 | Phase 2（时效性）→ Phase 5（基础设施） |
| **数据源混用** | 水位 ~240m（应为 ~460m） | Phase 5（内部缺陷）→ 切换数据源 |
| **参数硬编码** | 汛限 462.0m（参考值） | Phase 5（内部缺陷）→ 从 full_context 读取 |
| **告警风暴** | 1 小时 50+ 条 | Phase 5（误报）→ 调整阈值 |
| **三段式缺失** | 无【校验与依据】段 | Phase 1 → 补全模板 |
| **水位超限** | 462.8m > 462.5m | Layer 4 → **立即阻塞发布** |

## 快速参考

### 数据新鲜度标准

| 数据类型 | 最大允许延迟 | 超时处理 |
|---------|------------|---------|
| 水位 | 1 小时 | 立即告警 |
| 降雨预报 | 6 小时 | 标记"陈旧预报" |
| 告警 | 24 小时 | 升级人工 |

### 水位超限判断

```
ratio = current_rz / flood_limit

ratio >= 1.0 → ❌ 超限（P0，阻塞发布）
ratio >= 0.95 → ⚠️ 接近（P1，警告）
ratio < 0.95 → ✅ 正常
```

### 6 类根因 → 修复模式

| 根因 | 修复模式 |
|------|---------|
| 外部系统异常 | try-except + fallback + retry |
| 内部代码缺陷 | 精确修改 file:line |
| 数据问题 | 转工单 |
| 基础设施问题 | 配置调整 |
| LLM/模型异常 | Prompt 约束 |
| 预期行为（误报） | 合理降级（非掩盖） |
