# 水库四预系统诊断与验证 Skill v1.0

## 概述

本 Skill 提供完整的**诊断 → 验证 → 修复**闭环能力，服务于水库四预系统（forecasting、early-warning、plan-generation、simulation）。

### 核心能力

| 能力 | 描述 | 触发场景 |
|------|------|---------|
| **diagnose（诊断）** | 8 阶段结构化诊断流程 | 数据异常、告警误报、预案失败、系统错误 |
| **verify（验证）** | 6 层独立验证体系 | 输出验证、诊断验证、修复验证、跨域一致性 |
| **auto-fix（自动修复）** | 6 步自动修复流程 | 基于诊断结果自动生成并执行修复方案 |

---

## TL;DR（最高优先，每次回答都遵守）

> **诊断三原则**：
> ① **每个结论必须标注证据来源**，禁止"可能"、"大概"、"应该"
> ② **8 个 Phase 缺一不可**，跳过任何 Phase 都属于偷工减料
> ③ **区分"掩盖故障"和"合理降级"**：不能靠修复者自证

> **验证三原则**：
> ① **修复者不能给自己打分** — 必须换 Agent 独立验证
> ② **6 层验证缺一不可** — 跳过任何一层都会留下盲区
> ③ **验证通过的标准是可重现的证据** — 不是"看起来没问题"

> **修复三原则**：
> ① **最小化改动** — 只改必须改的地方
> ② **向后兼容** — 不破坏现有功能和接口
> ③ **最多 3 轮自动重试** — 超过 3 轮停止并升级人工

## 一、diagnose（诊断）— 8 阶段结构化诊断

### 适用场景

- 预报数据异常（数据不足、精度待评定、gated 状态）
- 预警误报/漏报（未确认告警堆积、告警风暴）
- 预案生成失败（参数异常、约束冲突）
- 预演结果不合理（敏感性分析超限、方案对比偏差）
- 系统性问题（数据源混用、硬编码参数、跨域关联失败）

### 8 阶段流程

详见 `references/diagnose-8phases.md`

#### Phase 0：澄清确认 ⚠️ 不能跳过

**目的**：确认诊断范围和时间边界

**输出格式**：
```
【Phase 0 完成】
- 问题类型：<分类>
- 时间范围：<起止时间>
- 影响范围：<涉及 skill/模块>
- 优先级：<P0/P1/P2>
```

**为什么不能跳**：
- 不确认时间范围就会分析错误时间段
- 不确认影响范围就会遗漏跨 skill 关联问题

---

#### Phase 1：全景扫描 ⚠️ 不能跳过

**目的**：收集全量数据，统计错误分布

**执行步骤**：
1. 验证数据源（使用正确的 query 脚本）
2. 按类型、级别、测站统计错误数量
3. 检查各 skill 输出是否满足验收标准

**输出格式**：
```
【Phase 1 完成】
- 数据源：<来源脚本>（✅ 正确 / ❌ 混用）
- 错误统计：<总数> 条（<分类>）
- 状态检查：<P0/P1/P2> 不通过项数
```

**为什么不能跳**：
- 不扫全景就会遗漏类别
- 不知道错误分布就无法识别突增/慢性/回归模式

---

#### Phase 2：数据质量检查 ⚠️ 不能跳过

**目的**：识别数据问题（缺失、异常、过时）

**检查维度**：
- **完整性**：数据覆盖率、缺失率
- **准确性**：数值范围、时间戳连续性、外键关联
- **时效性**：数据新鲜度（水位 <1h、降雨 <6h、告警 <24h）

**数据新鲜度标准**：
| 数据类型 | 最大允许延迟 | 超时处理 |
|---------|------------|---------|
| 水位 | 1 小时 | 立即告警 |
| 降雨预报 | 6 小时 | 标记"陈旧预报" |
| 告警 | 24 小时 | 升级人工 |

**输出格式**：
```
【Phase 2 完成】
- 完整性：<评分>（缺失率 <X>%）
- 准确性：<异常数量> 条
- 时效性：<过期数据数量> 条
- 数据质量评级：<优/良/中/差>
```

---

#### Phase 3：异常详情 ⚠️ 不能跳过

**目的**：提取完整的错误上下文（traceback + 输入参数）

**执行步骤**：
1. 提取完整 traceback（从顶层到根因）
2. 截取输入参数（SQL、API、触发条件）
3. **git log 交叉验证**：区分"新问题"还是"老毛病突然恶化"

**输出格式**：
```
【Phase 3 完成】
- 错误类型：<分类>
- 完整 traceback：<堆栈信息>
- 首次出现：<时间>（<git commit hash>）
- 历史同类问题：<有/无>
```

---

#### Phase 4：关联分析 ⚠️ 不能跳过

**目的**：跨域关联分析，识别复合问题

**分析维度**：
- **水位 × 降雨 × 渗流关联**：同时触发 → 大坝风险？
- **跨 skill 关联**：forecasting → early-warning → plan-generation
- **时间序列关联**：多个错误是否在同一时间窗口出现

**输出格式**：
```
【Phase 4 完成】
- 跨域关联：<水位+降雨+渗流 同时异常？>
- 跨 skill 关联：<涉及哪些 skill>
- 关联度评级：<高/中/低>
```

---

#### Phase 5：根因分析 ⚠️ 不能跳过

**目的**：6 类根因分类 + 证据链推理

**6 类根因**：

| 分类 | 特征 | 修复方向 |
|------|------|---------|
| **外部系统异常** | MCP 工具返回 Java stackTrace | try-except + fallback + retry |
| **内部代码缺陷** | TypeError/AttributeError 在 src/ | 精确修改 file:line |
| **数据问题** | 用户数据异常、表不存在 | 不修，转工单给 Owner |
| **基础设施问题** | 连接池超时、网络波动 | 配置调整（pool_size=10） |
| **LLM/模型异常** | 幻觉、编造不存在的表名 | Prompt 约束 + schema 校验 |
| **预期行为（误报）** | 确认后降级日志级别 | 合理降级（非掩盖故障） |

**证据链格式**：
```
[事实] <观测到的事实>
[推理] <推导过程>
[结论] <根因结论>
```

**区分"掩盖故障"和"合理降级"**：

| 行为 | 类型 | 判断标准 |
|------|------|---------|
| 把 `logger.error` 改成 `logger.warning` | ❌ 掩盖故障 | 错误未解决，只是不报了 |
| 降级为非实时数据源 + 记录降级日志 | ✅ 合理降级 | 有 fallback 机制，错误可追溯 |

---

#### Phase 6：影响评估

**目的**：评估问题的影响范围和严重程度

**评估维度**：
- **影响范围**：涉及哪些 skill/module、影响哪些用户/场景
- **严重程度**：P0 紧急/P1 高优/P2 普通
- **紧迫性**：是否在汛期/防洪关键期

---

#### Phase 7：修复建议

**目的**：输出短期止血 + 长期根治方案

**修复原则**：
- **短期止血**：立即执行（<1 小时），临时绕过或降级
- **长期根治**：本周内完成，修复根因
- **优先级**：P0（立即）/ P1（今日）/ P2（本周）

---

#### Phase 8：知识沉淀

**目的**：将诊断结果写入知识库，避免同类问题重复排查

**执行步骤**：
1. 写入知识库 `state/knowledge-base/root-cause-solutions.yaml`
2. 更新监控规则 `state/infrastructure-config/alert-rules.yaml`
3. 下次遇到同类问题：首次 48 分钟 → 有知识库后 15 分钟

---

### 诊断检查清单

完成诊断前，确认这 8 项：

- [ ] **Phase 0**：问题类型、时间范围、影响范围、优先级已确认
- [ ] **Phase 1**：数据源已验证、错误统计已完成
- [ ] **Phase 2**：完整性、准确性、时效性已检查
- [ ] **Phase 3**：完整 traceback 已提取、git log 已交叉验证
- [ ] **Phase 4**：跨域关联已分析
- [ ] **Phase 5**：6 类根因已分类、证据链已推理
- [ ] **Phase 6**：影响范围、严重程度、紧迫性已评估
- [ ] **Phase 7**：短期止血 + 长期根治方案已输出
- [ ] **Phase 8**：知识库已更新

## 二、verify（验证）— 6 层独立验证体系

### 适用场景

- 诊断报告的可信度验证
- 修复方案的有效性验证
- 预案/预演输出的安全性验证
- 跨 skill 数据一致性验证
- 法规符合性验证

### 6 层验证

详见 `references/verify-6layers.md`

#### Layer 1：数据源验证 🔍

**目的**：验证数据是否来自正确的来源

| Skill | 正确数据源 |
|-------|----------|
| forecasting | `query_forecast_data.py` |
| early-warning | `query_early_warning.py` |
| plan-generation | `query_plan_data.py` |
| simulation | `query_simulation_data.py` |

**通过标准**：
- ✅ 所有数值字段都标注了数据来源
- ✅ 无其他 skill 的数据源混入

---

#### Layer 2：格式规范验证 📝

**目的**：验证输出是否符合三段式要求

**检查内容**：
- 【依据】段存在（开头）
- 【分析】段存在（中间）
- 【校验与依据】段存在（结尾，绝对最后内容）

---

#### Layer 3：业务规则验证 📏

**目的**：验证输出是否符合业务规则和安全约束

**验证内容**：
- **水位约束**：范围合理（~450-465m）、计算正确
- **降雨约束**：量级分级正确、预见期合理
- **告警约束**：级别匹配、未确认告警统计完整
- **预案约束**：三组方案齐全、下泄量不超限

---

#### Layer 4：安全约束验证 🛡️

**目的**：验证是否违反水库安全红线

**验证内容**：
- **水位超限判断**：
  - ratio >= 1.0 → ❌ 超限（P0，阻塞发布）
  - ratio >= 0.95 → ⚠️ 接近（P1，警告）
  - ratio < 0.95 → ✅ 正常
- **下泄量约束**：不超下游安全泄量
- **调度优先级**：汛期防洪优先、非汛期兴利保供

---

#### Layer 5：跨域一致性验证 🔗

**目的**：验证多个 skill 之间的数据是否一致

**检查内容**：
- **水位一致性**：forecasting vs plan-generation（容忍误差 <0.1m）
- **汛限一致性**：forecasting vs early-warning（容忍误差 <0.01m）
- **告警与预案匹配**：early-warning vs plan-generation

---

#### Layer 6：法规符合性验证 ⚖️

**目的**：验证是否引用了正确的法规和标准

**必须引用的规范**：

| Skill | 必须引用的法规/标准 |
|-------|------------------|
| forecasting | GB/T 22482《水文情报预报规范》或 SL 250-2000 |
| early-warning | 《防汛条例》或 SL 224-2019 |
| plan-generation | 《防洪法》第41条或 GB 17621-1998 |
| simulation | GB 50201-2014《防洪标准》或《三岔水库调度规程》 |

---

### 验证检查清单

完成验证前，确认这 6 项：

- [ ] **Layer 1**：数据源正确，无 skill 混用
- [ ] **Layer 2**：三段式完整，规范引用准确，参数无硬编码
- [ ] **Layer 3**：数值在合理范围，计算逻辑正确
- [ ] **Layer 4**：水位未超汛限，下泄量未超限，调度优先级正确
- [ ] **Layer 5**：跨 skill 数据一致
- [ ] **Layer 6**：引用现行有效规范

## 三、auto-fix（自动修复）— 6 步自动修复流程

### 适用场景

当 diagnose（诊断）输出根因和修复建议后，触发本 Skill。

### 前置条件

1. ✅ diagnose 已完成：有完整的诊断报告（8 Phase）
2. ✅ 根因已分类：属于 6 类根因之一
3. ✅ 修复建议已输出：短期止血 + 长期根治方案
4. ✅ verify 已验证诊断：诊断结果可信

### 6 步流程

详见 `references/auto-fix-6steps.md`

| Step | 名称 | 关键动作 | 失败处理 |
|------|------|---------|---------|
| **Step 1** | 解析诊断报告 | 提取根因、修复建议、受影响文件 | 诊断不完整则停止 |
| **Step 2** | 查询知识库 | 匹配历史解决方案，复用经验 | 匹配度 <50% 则进入 Step 3 |
| **Step 3** | 生成修复方案 | 根据 6 类根因选择修复模式 | 方案不合理则重新诊断 |
| **Step 4** | 生成修复补丁 | 生成 diff 格式补丁 | 补丁不通过 lint 则打回 |
| **Step 5** | 执行测试 | 单元 + 集成 + 回归 + 性能 | **最多 3 轮**，失败则升级人工 |
| **Step 6** | 提交并部署 | 创建分支、提交 PR、触发预发 | 预发验证失败则打回 |

### 6 类根因对应修复模式

| 根因分类 | 修复模式 | 典型场景 |
|---------|---------|---------|
| 外部系统异常 | try-except + fallback + retry | MCP 工具超时 |
| 内部代码缺陷 | 精确修改 file:line | 数据源混用、硬编码参数 |
| 数据问题 | 不修，转工单 | 用户数据异常、表不存在 |
| 基础设施问题 | 配置调整 | 连接池超时、内存不足 |
| LLM/模型异常 | Prompt 约束 + schema 校验 | 幻觉表名 |
| 预期行为（误报） | 合理降级（非掩盖） | 告警过敏感 |

### 重试机制

```
第 1 轮：执行修复 → 测试 → 通过 ✅
第 2 轮：测试失败 → 调整方案 → 重测 → 通过 ✅
第 3 轮：测试失败 → 调整方案 → 重测 → 通过 ✅
第 4 轮：测试失败 → 停止 → 升级人工 ❌
```

**触发停止的条件**：
- 连续 3 轮测试失败
- 改动范围超出预期
- 性能严重退化（> 10 秒）
- 引入新的 P0 问题

## 四、验证 Skill（verify-*-output）— 各 skill 输出验收标准

本 Skill 提供各 skill 的输出验收标准，详见：

- `verify-forecast-output.md`：forecasting（预报）验收标准
- `verify-early-warning-output.md`：early-warning（预警）验收标准
- `verify-plan-output.md`：plan-generation（预案）验收标准
- `verify-simulation-output.md`：simulation（预演）验收标准

每个 Skill 包含 **P0/P1/P2** 三级检查：
- **P0**：必须通过，否则整题不合格
- **P1**：警告，需说明但可通过
- **P2**：优化建议，不影响通过

## 五、Goal 定义 — 完成条件与刹车

各 skill 的 Goal 标准写法，用于 Claude Code 的 `/goal` 命令，详见 `references/goals.md`。

**Goal 公式**：
```bash
/goal <任务描述>，满足以下条件：
   <证据项1>（可验证的完成标准）
   <证据项2>
   ...
   最多 <N> 轮；<刹车条件>
```

**关键要素**：
- **证据**：可验证的完成标准
- **刹车**：防止无限循环的停止条件
- **边界**：明确什么不能改/不能做

## 八、工作流示例

### 工作流 1：问题诊断 + 修复

```
问题发现
    ↓
diagnose（8 Phase 诊断）
    ↓
verify（验证诊断结果）
    ↓ 通过
auto-fix（6 Step 自动修复）
    ↓
```
